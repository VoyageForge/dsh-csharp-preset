# C# File and Class Organization

Source: Microsoft C# coding conventions, plus community style guides (justinwasilenko/Unity-Style-Guide, Richard Fu).

## The one rule that matters most

**One type per file.** Every class, interface, enum, record, and struct gets its own `.cs`
file, and the file name matches the type name exactly: `OrderService.cs` holds `OrderService`,
`IOrderRepository.cs` holds `IOrderRepository`. Do not stack multiple public types in one file.

This is the rule agents break most often. When you would add a second type, create a new file
instead — even for a small helper class or enum.

## When to split a class (it is too big when...)

- **More than one responsibility.** A class that both fetches data and formats it, or validates
  and notifies, is doing two jobs. Extract each job into its own type and have the original
  coordinate them. (See the `solid-review` skill.)
- **More than roughly 200 lines** (a guideline, not a hard number). Beyond that, split along
  responsibility, not arbitrarily.
- **A method over ~20 lines** doing several steps. Extract named private methods first; if the
  steps belong to different concerns, move them to a helper type.

How to split:
1. Identify the distinct concerns (e.g. input parsing, validation, persistence, output).
2. Extract each concern into a new class/interface in its own file.
3. Inject the extracted types through the constructor (dependency injection), do not `new` them
   inline.
4. Keep the original class as a thin coordinator.

## Partial classes — use sparingly

`partial` lets one type span multiple files, but it exists mainly for **code generation**
(designer files, source generators) where a tool owns one file and you own the other.

- Use `partial` when a generated file and a hand-written file must contribute to one type.
- Do **not** use `partial` just to "organize" a large hand-written class. That hides the problem
  instead of fixing it — split into real types instead.

```csharp
// OrderService.cs        (hand-written)
public partial class OrderService
{
    public async Task<Order?> GetByKey(Guid key, CancellationToken ct) => await _repo.GetByKey(key, ct);
}

// OrderService.Generated.cs   (generated by a tool — do not hand-edit)
public partial class OrderService
{
    private readonly IOrderRepository _repo;
}
```

## Namespaces vs folders

- Folder structure should mirror namespaces: `Acme.Product/Application/Handlers/OrderHandler.cs`
  uses `namespace Acme.Product.Application.Handlers;`.
- Use **file-scoped namespaces** (`namespace X;`) — not block-scoped — to save one indentation level.
- One namespace per file in almost all cases. Multiple namespaces in one file is a smell.

## Member ordering inside a class

Keep a consistent order so a reader knows where to look (from Unity Style Guide / common C# practice):

1. Constants
2. Static fields
3. Instance fields
4. Constructors
5. Properties
6. Events / delegates
7. Public methods
8. Private methods
9. Nested types

Within each group, order by access: `public`, `internal`, `protected`, `private`.

## Example: the right way to add a second type

```csharp
// OrderService.cs
namespace Acme.Product.Application.Handlers;

public class OrderService(IOrderRepository repo, IOrderNotifier notifier)
{
    public async Task<bool> AddItem(long orderId, long productId, CancellationToken ct)
    {
        // Coordinate two extracted responsibilities; keep no data/formatting logic here.
        var order = await repo.GetById(orderId, ct);
        if (order is null || order.ItemCount >= order.MaxItems) return false;
        await repo.AddItem(orderId, productId, ct);
        await notifier.SendOrderUpdated(orderId, ct);
        return true;
    }
}
```

```csharp
// IOrderNotifier.cs
namespace Acme.Product.Application.Interfaces;

public interface IOrderNotifier
{
    Task SendOrderUpdated(long orderId, CancellationToken ct);
}
```

```csharp
// IOrderRepository.cs
namespace Acme.Product.Domain.Interfaces;

public interface IOrderRepository
{
    Task<Order?> GetById(long orderId, CancellationToken ct);
    Task AddItem(long orderId, long productId, CancellationToken ct);
}
```

Each type is one file, each has one responsibility, and the folder path matches the namespace.

## What not to do

- Do not put a class, an interface, and an enum in one file.
- Do not use `partial` to split a large hand-written class — split into real types.
- Do not nest unrelated types just to avoid a new file.
- Do not grow a single method past ~20 lines without extracting.
